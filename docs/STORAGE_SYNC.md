# Хранилище и синхронизация в eSCore

`eSCore` решает две разные задачи:

- постоянное хранение данных игроков;
- синхронизацию runtime-значений между серверами и между перезагрузками.

Эти задачи специально разделены, потому что backend и sync не всегда совпадают по требованиям.

## Какие backend'ы поддерживаются

Основной модуль умеет работать с:

- JSON
- SQLite
- MySQL

Выбор backend делается через `storage.backend` в `config.yml`.

## Дефолтные имена

Для новой установки используются такие значения по умолчанию:

- SQLite file: `escore.db`
- SQLite table: `escore_values`
- MySQL database: `escore`
- MySQL table: `escore_values`

Это публично-нормализованные имена под бренд `eSCore`.

Если вы мигрируете старую установку `WScore`, можно оставить старые таблицы и имена вручную через конфиг.

## Когда использовать какой backend

JSON:

- подходит для тестов и очень маленьких серверов;
- не лучший вариант для многосерверной среды;
- удобен как самый простой backend.

SQLite:

- хороший дефолт для одного Paper-сервера;
- не требует отдельной СУБД;
- удобен для большинства локальных или средних установок.

MySQL:

- нужен, если backend должен быть общим для нескольких серверов;
- подходит для production multi-server setup;
- обычно используется вместе с Redis runtime sync.

## Что хранится в backend

В backend попадают только значения тех скриптов, которые используют persistence mode `backend`.

Это важно:

- не каждый placeholder обязан храниться постоянно;
- formatters и memory-only логика не обязаны записываться в базу;
- `eSCore` различает runtime value и persisted value.

## Flush и batching

`eSCore` не обязан писать каждое изменение мгновенно в backend.

Для backend-persistent script'ов используется схема:

- значение меняется в памяти;
- формируется pending write;
- write попадает в flush queue;
- запись уходит в backend, когда наступает время flush.

Это позволяет:

- уменьшить количество write операций;
- сгладить burst-изменения;
- не дёргать базу при каждом событии.

JSON-файл записывается через временный файл и атомарную замену, поэтому аварийная остановка во время сохранения не должна оставлять наполовину записанный JSON. При reload сначала сбрасываются накопленные pending writes, а не отбрасываются.

## Polling fallback

Для shared backend можно включить database polling fallback.

Идея такая:

- если Redis не используется;
- но backend общий;
- `eSCore` может периодически опрашивать backend на предмет remote updates.

Это не так быстро, как Redis runtime sync, но даёт рабочую синхронизацию для shared storage.

Удаления в SQL сохраняются как `null`-tombstone с timestamp: иначе удалённая строка исчезла бы до того, как другие серверы увидят изменение. Параметр `sync.database-poll-overlap-millis` задаёт небольшое перекрытие окон polling, чтобы не пропустить транзакцию, которая началась до опроса, но завершилась после него. Повторно увиденные записи отсекаются по timestamp.

## Redis runtime sync

Redis нужен не как основной backend, а как runtime-канал синхронизации.

По умолчанию используются:

- channel: `escore:sync`
- key-prefix: `escore`

Через Redis `eSCore`:

- публикует изменения локальных runtime-значений;
- хранит временные runtime-снимки для быстрых remote reads;
- может подгружать runtime-value при join/prefetch.

## Когда нужен Redis

Redis полезен, если:

- у вас несколько Paper-серверов;
- значения должны расходиться между ними быстро;
- scoreboard/placeholder state должен быть свежим, а не только после backend poll;
- нужен runtime cache поверх MySQL.

Если сервер один, Redis часто не нужен.

## Prefetch на входе игрока

При входе игрока `eSCore` может:

- префетчить persistent backend values;
- префетчить Redis runtime values.

Это снижает шанс, что первый запрос к placeholder'у попадёт в пустой cold state.

## Режимы sync

Скрипт может использовать один из режимов:

- `none`
- `redis`
- `database`
- `auto`

Режим `auto` удобен тем, что `eSCore` сам выбирает поведение:

- если Redis включён, используется Redis;
- если backend shared, можно использовать database sync;
- если сервер локальный и shared sync не нужен, sync можно не включать.

## Что считается shared backend

Shared backend — это backend, который доступен нескольким серверам одновременно.

Обычно это:

- MySQL

SQLite и JSON в типичном deployment не считаются shared backend.

## Как `eSCore` объединяет изменения

Если одно и то же значение меняется много раз за короткий промежуток, `eSCore` может записать в backend уже последнюю версию, а не каждое промежуточное состояние.

Это ожидаемое поведение.

Задача backend — хранить актуальное значение и timestamp, а не журнал всех промежуточных шагов.

## Per-server счётчики в shared backend

Для multi-server сценария `eSCore` поддерживает server-scoped хранение.

Если в скрипте включён флаг:

```js
serverScoped: true
```

то поведение будет таким:

- каждый сервер пишет своё значение отдельно;
- обычный placeholder читает агрегированное значение со всех серверов;
- placeholder с суффиксом `__server` читает только значение текущего сервера.

Это нужно для кейсов вроде:

- общего времени в игре;
- статистики убийств по сети серверов;
- накопительных счётчиков, которые обновляются на нескольких серверах одновременно.

Без `serverScoped: true` shared backend всё равно будет общим, но локальный и глобальный режимы для такого ключа обычно будут совпадать, потому что данные не разделены по `server-id`.

## Runtime TTL в Redis

Для Redis runtime-sync используется TTL.

Он нужен, чтобы:

- не хранить старые runtime entries бесконечно;
- позволять актуальным значениям вытеснять устаревшие;
- уменьшать мусор в Redis.

Если TTL истёк, backend всё равно остаётся главным источником persistent-данных, если скрипт backend-persistent.

## Конфигурация LuckPerms contexts

Некоторые storage key могут использоваться не только как backend-данные, но и как источник context bridge для LuckPerms.

Теперь дефолтные context key ориентированы на:

- `escore:dragon-kills`
- `escore:dragon-kills-bucket`
- `escore:has-dragon-kill`

Это не мешает вам оставить старые `wscore:*` имена вручную в конфиге, если миграция уже идёт на работающем сервере.

## Типичный single-server сценарий

Для одного сервера обычно хватает:

- `storage.backend: sqlite`
- Redis выключен
- polling fallback не важен

Это даёт простой и устойчивый режим.

## Типичный multi-server сценарий

Для нескольких серверов обычно лучше:

- `storage.backend: mysql`
- `sync.redis.enabled: true`
- одинаковые storage-конфиги на всех серверах
- уникальный `server-id` для каждого инстанса

Это позволяет и хранить, и быстро синхронизировать значения.

Если вам нужно одновременно получать и локальное значение, и сумму по всей сети, используйте shared MySQL вместе со скриптами, у которых включён `serverScoped: true`.

## Миграция со старого WScore

Если раньше использовались:

- `wscore.db`
- `wscore_values`
- `wscore:sync`
- `wscore` как Redis prefix

их можно оставить, если продакшен уже к ним привязан.

Но для новых установок лучше использовать новые дефолты `escore.*`.

## Практическая рекомендация

Начинайте с простого:

- SQLite для одного сервера;
- MySQL + Redis для нескольких;
- backend persistence только для тех скриптов, которым это действительно нужно;
- новые имена `escore`, а не `wscore`.

## TTL, namespaces и перенос данных

Публичный API поддерживает изолированные пространства ключей:

```java
var storage = eScoreProvider.get().storage("my-plugin");
storage.set(playerId, "session", value, Duration.ofMinutes(10));
Object value = storage.get(playerId, "session", null);
```

TTL хранится в JSON, SQLite и MySQL и передаётся через Redis. Старые SQL-таблицы автоматически получают колонку `expires_at`, а старые JSON-файлы читаются с бесконечным TTL.

Настраиваемые лимиты защищают от чрезмерного числа ключей, длинных имён, больших значений и слишком крупных batch-запросов.

```text
/escore storage status
/escore storage flush
/escore storage export <name>
/escore storage import <name> --confirm
```

Файлы переноса находятся в `plugins/eSCore/exports`. Import выполняет контролируемое слияние и требует явного `--confirm`. Формат содержит `schemaVersion`, поэтому несовместимый экспорт не применяется молча.

Redis subscriber после разрыва соединения восстанавливается с экспоненциальной задержкой до 30 секунд; его состояние видно в `/escore diagnose`.
